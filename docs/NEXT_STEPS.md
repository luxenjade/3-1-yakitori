## P0: 本番データ連携

### 1. 顧客用の仮注文APIを追加する

現在、仮注文作成は `mockStore.createTemporaryOrder()` のみで行われている。匿名利用者が安全に仮注文を作成できる Edge Function または SECURITY DEFINER RPC を作る。

- 商品・在庫・数量をサーバー側で検証し、`temporary_orders` と `temporary_order_items` を原子的に作成する。
- 6桁コードの衝突時は再生成する。
- QRに含めるのは必要最小限の注文ID・短縮コードにする。
- 有効期限切れ仮注文を定期削除するジョブも用意する。

完了条件: モバイル画面で作った仮注文を、別端末のPOSがQRと手入力の両方で取得できる。

### 2. フロントエンドの状態管理をSupabase対応に置き換える

`src/store/store-context.tsx` は現状モック固定であり、`src/lib/api.ts` のSupabase分岐も会計だけである。デモモードを維持しつつ、環境変数設定時はリモートストアを使用する構成にする。

- 商品、注文、注文明細を取得するリポジトリ／ストアを実装する。
- `createTemporaryOrder`、仮注文検索、会計、ステータス進行、受け取り確認をAPI経由に統一する。
- `items`、`orders`、`order_items` の変更をSupabase Realtimeで購読し、各画面を更新する。
- 顧客画面は自分の注文だけを追跡できるよう、ブラウザ側に注文識別子を安全に保持する。全注文データは公開しない。

完了条件: リロード・別端末・別ブラウザでも、各画面に同じ在庫と注文状態が反映される。

### 3. Edge FunctionとDB契約を実機で確認する

- Supabaseプロジェクトに全migrationを適用し、3つのEdge Functionをデプロイする。
- `.env.example` を追加し、利用する変数名を統一する。フロントエンドは `VITE_SUPABASE_URL` と `VITE_SUPABASE_ANON_KEY` を使用する。
- 会計RPCの入力値（決済種別、注文元、数量）を厳格に検証する。重複商品行は集約し、数量は正の整数だけ許可する。
- 失敗時のAPIレスポンス形式を `ok` / `message` / `order` で統一する。

完了条件: 同時会計でも在庫が負にならず、失敗理由がPOSに表示される。

## P0: 認証・権限制御

### 4. スタッフログインと画面ガードを実装する

RLSには `pos`、`kitchen`、`signage`、`admin` のロールがあるが、ログインUI・ルート制御は未実装。

- Supabase Authでスタッフ用ログイン／ログアウトを実装する。
- `/pos` は POS・admin、`/kitchen` は kitchen・admin、`/signage` は signage・admin に限定する。
- サイネージに注文詳細や受け取りトークンを出さないことを確認する。
- 本番の共有アカウント運用方針（パスワード、端末ロック、当日後の無効化）を決める。

完了条件: 未ログインまたは権限外ユーザーがスタッフ画面・運用APIを使えない。

### 5. RLS／RPCの安全性を見直す

- SECURITY DEFINER関数に `SET search_path = public` を設定する。
- `app_role` と `has_role` を参照するmigration順序を、空のDBでも失敗しない形に整理する（現状は `002_checkout_rpc.sql` が `004_auth_roles_and_rls.sql` の型・関数に依存）。
- 顧客に必要な商品読み取り以外のテーブルアクセスが許可されていないことを確認する。
- Edge Functionがservice roleをブラウザへ露出していないことを確認する。

完了条件: 新規Supabaseプロジェクトへmigrationを順番に適用でき、ロール別の許可・拒否テストが通る。

## P0: 当日運用テスト

### 6. リハーサルシナリオを作成・実施する

最低限、次のケースを実端末と本番相当のSupabase環境で確認する。

1. QR仮注文を会計し、厨房・サイネージ・顧客画面へ即時反映される。
2. POS直接入力、QRスキャン、短縮コード入力の各会計ができる。
3. 同一仮注文の二重会計と、在庫不足時の会計が拒否される。
4. 厨房の `pending → cooking → ready → completed` と、誤完了からの復元が意図どおりに扱える。
5. 受け取りコードの不一致、期限切れ、使用済みが拒否される。
6. 回線断・復帰、端末リロード、カメラ拒否時にスタッフが業務を継続できる。
7. 完売時に顧客・POS・サイネージの表示が一致する。

完了条件: テスト担当者、日時、結果、対応事項を残し、重大不具合が解消される。
